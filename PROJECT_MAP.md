# PROJECT_MAP — конструктор маршрутов метро СПб

Что за проект: сайт-конструктор текстовых пошаговых маршрутов по станциям метро
Санкт-Петербурга для незрячих пользователей (проверено с NVDA, VoiceOver, TalkBack).
Пока только Московско-Петроградская линия, только в пределах одной линии, без пересадок.
Статус работы (что сделано / в планах) — в PROGRESS.md, сюда его не дублируем.

Путь к проекту: `D:\projects\git_rep\metro`

## Структура файлов

```
metro/
├── index.html              — главная страница, форма выбора станций
├── instructions.html       — страница "Инструкция"
├── about.html               — страница "О нас"
├── PROGRESS.md              — статус: сделано / в планах
├── PROJECT_MAP.md           — этот файл
├── css/
│   └── style.css            — тема из prefers-color-scheme, без ручного переключателя
├── js/
│   ├── data-loader.js       — loadMetroData(): читает lines.json + все station/*.json
│   ├── route-builder.js     — buildRoute(): вся логика направления и сборки маршрута
│   ├── combobox.js           — createStationCombobox(): поле поиска станции + список кнопок-вариантов
│   ├── app.js                — связывает данные, combobox.js и вывод результата на index.html
│   ├── instructions.js       — раскрывающиеся блоки инструкции по устройствам
│   └── nav.js                 — общее меню сайта, подставляется на все три страницы
└── data/
    ├── lines.json            — список линий, у каждой line.stations = массив id по порядку
    └── stations/*.json       — по одному файлу на станцию
```

Запуск: `cd metro && python -m http.server 8000`, открыть `http://localhost:8000/`.
Открывать `index.html` напрямую (`file://`) нельзя — `fetch()` не читает локальные
файлы из-за CORS. Правка JSON не требует перезапуска сервера — он не кеширует,
достаточно F5 (при проблемах — Ctrl+Shift+R).

## Схема станции (data/stations/<id>.json)

```json
{
  "id": "prospekt-prosveshcheniya",
  "name": "Проспект Просвещения",
  "line_id": "line2",
  "order": 2,                       // позиция станции на линии, см. lines.json
  "status": "ok",                   // "no_data" — станция в списке, но выбрать нельзя
  "closed_type": false,             // true — платформа закрытого типа (ограждена)
  "notes": null,
  "entrance": { "steps": [ ... ] },
  "platform": {
    "steps": [ ... ],
    "directions": [
      { "side": "right", "destination": "Купчино" },
      { "side": "left", "destination": "Парнас" }
    ]
  },
  "exit": { "steps": [ ... ] }
}
```

`directions` — с какой стороны платформы (при входе на неё) едут поезда в каждую
сторону. Используется ТОЛЬКО для посадки на станции отправления (какая сторона
нужна, чтобы сесть в правильный поезд) — см. buildRoute(). Для определения
поворота на выходе НЕ годится: проверено на всех станциях с данными, что связь
между стороной посадки и поворотом на выходе не единообразна — на Озерках это
«та же сторона», а на Петроградской/Горьковской/Пионерской/Просвещении —
«противоположная сторона». Значит поворот на выходе — независимый факт по
каждой станции конкретно, доверять можно только каноническому docx-документу
или личной проверке на месте, а не выведению по формуле от `directions`.
Терминал линии (order===1) имеет только одну запись в directions с `side: null`.

### Формат шага (entrance.steps / platform.steps / exit.steps)

```json
{ "text": "Идти прямо до лестницы" }                                  // безусловный
{ "when": { "arrival_from": "Парнас" }, "text": "Поверните направо" } // условный
```

`when` — открытый набор условий; сейчас используется только `arrival_from`
(с какой стороны линии прибыл поезд). При добавлении пересадок можно будет
добавить новые ключи (например `transfer_to`) не трогая движок — он сравнивает
произвольный набор пар ключ/значение (см. `stepMatches()` в route-builder.js).

Для станций с двумя выходами на разных концах платформы (например Проспект
Славы — таких станций пока нет в маршрутах) схему `when` придётся расширить
(например ключом вроде `exit_side`) — пока не реализовано.

## Логика движка (js/route-builder.js)

`buildRoute(fromId, toId, stations, lines)`:

1. Проверки: станции не совпадают, обе есть в данных, обе `status !== "no_data"`,
   обе на одной линии (иначе — ошибка "маршруты только в пределах одной линии").
2. Направление: сравнивает `order` станций А и Б в `line.stations`.
   - Терминал линии (station с order===1) даёт два опорных названия:
     `labelNear` = имя терминала (например "Парнас"),
     `labelFar` = единственное значение в его `directions[0].destination`
     (например "Купчино"). Без хардкода конкретных станций — работает для
     любой линии с таким же устройством данных.
   - `movingForward = order(Б) > order(А)`.
   - `destinationLabel` (куда едем) = labelFar если movingForward, иначе labelNear.
   - `arrivalFrom` (откуда приехал поезд) = labelNear если movingForward, иначе labelFar.
3. `context = { arrival_from: arrivalFrom }` — передаётся в `resolveSteps()`,
   который фильтрует шаги по `when` и возвращает `{text, conditional}[]`
   (`conditional` нужен интерфейсу, чтобы понять, какой шаг — тот самый условный
   поворот на выходе, и добавить к нему приставку "После выхода из поезда").
4. `boardingSide` — сторона посадки на станции А: ищется в `from.platform.directions`
   запись с `destination === destinationLabel`.
5. Возвращает `{ fromName, toName, entranceSteps, fromPlatformSteps, toPlatformSteps,
   exitSteps, boardingSide, arrivalFrom, destinationLabel }` — каждый *Steps это
   массив `{text, conditional}`.

## Выбор станции (js/combobox.js)

`createStationCombobox({ input, resultsContainer, resultStatus, options, emptyMessage })`
— используется дважды на index.html (для «Станция отправления» и «Станция назначения»).

- `options` — полный список станций линии в порядке вывода (`{id, label}`), станции
  `status: "no_data"` включены с пометкой «(данных пока нет)».
- По мере набора текста в `input` список в `resultsContainer` фильтруется по
  вхождению подстроки (без учёта регистра) и перерисовывается как набор обычных
  `<button>` — по одной на подходящую станцию.
- Выбор станции требует явного нажатия на кнопку варианта (кликом или
  Tab+Enter/пробел) — просто напечатанный текст выбором не считается,
  `getSelectedId()` в этом случае вернёт `undefined`, что `app.js` ловит перед
  построением маршрута и показывает понятную ошибку вместо тихого провала.
- **Почему не ARIA `role="combobox"`/`role="listbox"`**: первая версия была
  сделана по этому стандартному паттерну, но на практике (проверено вручную)
  она ненадёжно работает с сенсорными читалками — touch-жесты вокруг поля
  ввода закрывали список раньше, чем пользователь успевал до него добраться,
  список не всегда оказывался доступен свайпом. Версия на обычных `<button>`
  устраняет весь этот класс проблем: кнопка — самый простой и одинаково
  надёжно поддерживаемый элемент везде, без специальных ARIA-паттернов.
  Список результатов сознательно НЕ закрывается по потере фокуса полем —
  чтобы можно было спокойно touch-исследовать его пальцем.
- `setSelectedId(id)` (программная установка — используется при заполнении
  формы по умолчанию и кнопкой «⇄») намеренно НЕ вызывает `input.focus()` —
  раньше это дважды подряд вызывало смещение фокуса в конец при инициализации.

## Вывод маршрута (js/app.js → renderRoute)

Структура на странице (без пересадок):

```
h2  Маршрут: {А} → {Б}
p   Шагов: N
h3  Вход: {А}
    ...entranceSteps
h3  На платформе: {А}
    [Поезда в направлении «X» отправляются слева/справа — если boardingSide есть]
    ...fromPlatformSteps
    Дождитесь прибытия поезда и войдите в вагон.   (константа BOARD_TRAIN_STEP)
h3  Выход: {Б}
    ...exitSteps (первый conditional-шаг — с приставкой "После выхода из поезда ...")
```

Секция «На платформе: {Б}» НЕ выводится (нужна будет только при пересадках —
`toPlatformSteps` уже считается в движке, просто не рендерится).

`#result` — НЕ aria-live (иначе NVDA зачитывает весь маршрут разом при нажатии
кнопки). Озвучивается только короткое подтверждение через `#status`
(role="status" aria-live="polite") — и только по действию пользователя
(маршрут построен / ошибка / поменяли местами), не при загрузке страницы.

`setStatus()` перед установкой нового текста сначала очищает `#status`, и только
следующим тиком (через `setTimeout`) ставит новый — иначе повторно одинаковый
текст (например «Маршрут построен.» дважды подряд) NVDA не озвучит: браузер не
видит изменения в дереве доступности, если текстовый узел не поменялся.

## Инструкция (instructions.html + js/instructions.js)

Раскрывающиеся блоки по устройствам (Windows/Android/iPhone) — паттерн ARIA
disclosure: кнопка `.device-toggle` с `aria-expanded`/`aria-controls`, панель
`.device-panel` скрыта атрибутом `hidden`. Кнопка работает как тумблер — открывает
и закрывает одним и тем же нажатием, отдельной кнопки «Свернуть» внутри панели
нет (была, убрана: с ней у NVDA иногда терялся фокус после активации стрелками
в режиме чтения, а не табом — тумблер эту задачу решает без такого риска).

Если после активации кнопки-тумблера потребуется программно переносить фокус
(например, если кнопка «Свернуть» всё же понадобится снова в будущем) — вызывать
`focus()` нужно через `setTimeout(..., 0)`, а не синхронно в обработчике клика:
иначе NVDA не успевает переключиться из Browse Mode в Focus Mode, и виртуальный
курсор чтения съезжает к следующему видимому месту в документе.

## Общее меню (js/nav.js)

Генерируется один раз в `js/nav.js` и подставляется на все три страницы через
`<div id="site-nav"></div>` в `<header>`. Список пунктов меню (порядок, названия,
ссылки) правится в одном месте — `pages` в начале файла. Ссылка на текущую
страницу (сравнение по имени файла из `location.pathname`) получает
`aria-current="page"` — читалки озвучивают её как «текущая страница».
